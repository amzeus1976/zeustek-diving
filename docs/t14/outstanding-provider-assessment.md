## Existing fallback, provenance and selection

The source of truth is [the conditions service](../../lib/server/conditions/service.ts), [provider adapters](../../lib/server/conditions/adapters.ts), [bounded transport](../../lib/server/conditions/transport.ts), [conditions model/selection](../../lib/weather/conditions-model.ts) and [existing configuration UI](../../components/weather/conditions-configuration.tsx).

- Auto adds only enabled providers and respects explicitly disabled providers. A manual provider request can attempt an already configured but unverified integration; failure adds a redacted diagnostic while Open-Meteo readings remain available. SwellCloud's registry shows `disabled`; an attempted manual choice currently yields `unconfigured` with the same approval reason and issues no SwellCloud request.
- HTTP 401/403 becomes a fixed `denied` diagnostic without the upstream response body or credential. Credentialed requests cannot redirect to an unsupported destination. Existing bounded transport applies timeout, body limits, server cache and rate-limit retry suppression. No provider response is used as a readiness assessment.
- Met Office preserves returned GeoJSON coordinates, model run and hourly UTC validity. Absent marine/depth fields remain absent. Its attribution is retained. A mocked compatible response proves parsing only, not current endpoint access or subscription validity.
- Copernicus sends latitude, longitude, date and planned depth to the fixed internal subset binding. It uses a 12-second abort signal, bounded transport body and a further 500,000-character subset limit. Its adapter examines at most 200 samples and retains dataset identity, returned sample coordinates, valid UTC time, retrieval time, units, exact returned depth or explicitly bottom temperature. `thetao` without a non-negative returned depth is not converted to a planned-depth temperature. A missing dataset or absence of supported readings produces `unsupported` and preserves fallback.
- Direct Copernicus readings and Open-Meteo Marine's Copernicus-derived products remain separately attributed. Open-Meteo surface temperature remains surface data. Values from competing sources are retained for inspection; Auto selects by metric/depth/datum, geographic and temporal coverage, freshness and source class without averaging them.
- Explicit access checks retain a redacted diagnostic, fingerprint and 24-hour expiry in separate `weather_provider_checks` runtime metadata. Status hydration only selects existing rows; it does not create a schema or change canonical owner records. Missing metadata storage leaves a provider unverified across server restart.

## Limits requiring review before any future activation

The existing bridge request sends a date and planned depth but not the requested time, dataset ID/version, variable names or mode. The bound service must return relevant timestamps for local selection and establish a concrete dataset contract before activation. The app labels the result with `dataset` but does not independently retain dataset version, model-run or a dataset-specific resolution; those details must not be asserted unless supplied through a reviewed contract. Structural normalisation is not complete external schema validation: finite coordinates/string timestamps and numeric depth alone do not establish provider product accuracy. Selection rejects unavailable or irrelevant readings rather than inventing coverage.

Copernicus access fingerprints identify binding presence (`true`), not the deployed bound service's identity/version. A replacement binding could inherit a prior successful check until expiry. Before activating or changing a bound service, explicitly repeat the compatible product check and review a versioned identity/invalidation design. This limitation is presently inactive because the accepted state records no binding. No source change was made to obscure or prematurely resolve it.

The bridge's abort signal is supplied to the bound service; enforcement by the actual service remains unverified. SwellCloud public documentation indicates potentially slow initial data retrieval, so the accepted transport timeout cannot be presumed compatible. Complete latency, cancellation, payload, retry, quota and attribution checks require a separately approved provider contract. No fallback fixture establishes production freshness, access, compatibility or availability.
