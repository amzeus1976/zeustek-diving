# Public profile and read-only API — bounded implementation/security plan

This is the #81 front-page/profile slice of #50 plus #82. No Gas Plan shares, calendar export, data-health centre, automatic publication, additional login provider or live-updating public record graph. Owner review is required before feature code. Production profile content and real integration keys need later distinct confirmations.

## Inspected boundaries

app/page.tsx gates the dashboard through Sites ChatGPT identity and household allowlist. app/chatgpt-auth.ts validates return paths; lib/server/household.ts identifies the owner separately from a household member. Private APIs and R2 certification images enforce identity independently. Canonical records remain account-scoped Dexie plus owner-scoped D1 dive_records; backup allowlists exclude server secrets. Existing image crop metadata is reusable without changing source images. app/service-worker.ts currently caches root navigation; that cache must cease storing the identity-dependent/public root and public publication resources to prevent revoked/private landing content replay.

## Public publication contract

- Dedicated server publication artifact in the existing D1 binding (dive_publications), not a Person store. One landing slot owned by the registered household owner. Version 1, enabled flag, published/updated times, opaque publication/photo IDs and strictly validated JSON. No canonical IDs in public content.
- Initial opt-in fields: selected display name, plain-text biography (bounded length), photo derivative, total logged Dives, logged minutes, maximum logged depth and highest recreational DISPLAY award. Statistics carry source wording/scope/as-of time. No capability/depth permission derived from award rank. No automatic change when private records change.
- Client editor under existing Settings selects from local owner evidence, builds the allowlisted snapshot and previews it with the same presentation component as the anonymous page. Server validates exact fields/types/ranges/lengths, rejecting unknown/nested sensitive data. Explicit Publish/Update asks owner to approve that exact preview; Revoke atomically disables the slot. Disabled/no row is the default.
- Root: approved signed-in users retain the existing dashboard and all query deep links. Anonymous/unapproved root receives the isolated landing or generic welcome with existing ChatGPT sign-in. Private section/record queries authenticate and preserve a validated return path; unapproved accounts see the welcome/access explanation without redirect loops. Public renderer imports no private dashboard/store. /public-profile is a deliberate visitor preview independent of login.
- Owner-selected photo is decoded/cropped client-side into a bounded JPEG/PNG raster without metadata, then server rejects unsupported/oversized formats. Store in existing R2 FILES under a publication-only random key. Public photo endpoint resolves only the current enabled publication's opaque photo ID; never accepts private attachment keys. No listing. Revoke/photo replacement makes old ID inaccessible. Original private image is unchanged.
- Page/JSON/photo responses private/no-store, noindex and restrictive referrer policy. Public/root excluded from service-worker caching; private API remains NetworkOnly. Preview is not a public write. Revocation prevents future service access but cannot erase visitor copies.

## API contract and key storage

- Versioned GET/HEAD /api/v1/dives, /awards, /equipment, /equipment-usage with strict selected-record DTOs. Other methods return 405. No unrestricted records/backup handler, no private note/contact/team/serial/certification-number/medical/emergency/plan/trip/source-import fields.
- Owner-only Integration Keys settings, existing ChatGPT identity, explicit client name AMZeus/ZeusTek, scopes and selected canonical record IDs. Dives consent includes whether dates/site display/depth/duration/mode are included; award consent title/agency/date/track; equipment name/category/maker/model; usage only selected saved evidence. Unknown fields rejected. No key issued by rendering/settings reads.
- Credentials and object mappings in separate server tables outside canonical record/backups: dive_api_keys and dive_api_objects (and selected consent metadata). Key includes random public identifier plus 256-bit random secret; only SHA-256 verifier retained, fixed-length digest comparison, no plaintext recovery. High entropy makes offline hash guessing infeasible; no new browser/public environment secret. Show full key once after explicit creation/rotation; never store it in browser local storage. Expiry required; revoke immediately; rotate revokes old key atomically while adding replacement.
- Every data query derives owner from the verified key, not a request owner parameter. Joins consent and current canonical record owner/kind/deleted state. API object IDs are independent random mappings scoped to that owner's consent, not account/import IDs. Missing/revoked/other-owner objects uniformly unavailable. Key cannot read partner/shared-household records merely because private gear UI can.
- Existing server-readable canonical data is projected only after validated shapes. If encrypted/unavailable, report unavailable instead of changing encryption. No canonical writes during read. Confirmed usage comes from saved equipmentIds and equipmentSetApplications snapshot slots; equipmentSetId alone never consults today's set. Explicit hire/absent evidence yields hire/unknown; missing/deleted unselected gear is not disclosed. Units metres/minutes; dates retain original resolution; provenance distinguishes direct links/saved snapshot/unknown.
- Deterministic ordering and limit 1–100 (default25), signed owner/key/resource-bound cursor; tampered/filter-mismatched cursors fail safely. Global atomic D1 minute counter per key gives bounded request rate, with safe429/Retry-After; no unreliable per-isolate-only quota. No arbitrary SQL/query filters. Bound record/image/body/response sizes. OpenAPI3.1 GET contracts with dummy examples, safe401/403/404/405/429/503 errors.
- Authorization Bearer header only over HTTPS, never query keys, no permissive credentialed CORS. Responses private/no-store and NetworkOnly PWA. Metadata contains only client/scopes/creation/expiry/status/last-use; no token/verifier export or log. Owner settings use same-origin/Origin validation for writes. Error bodies exclude SQL, headers, canonical JSON, upstream messages.

## Tests and abuse cases

Security review refinements from the preserved source: the private household setup currently contains literal household names/contact details in client source. Before a public landing release, remove those literals from client artifacts and obtain permitted display details through the authenticated household status response; absent details use generic wording. Do not import the dashboard, private store or household identities into the public renderer. Check anonymous HTML, client artifacts and response DTOs independently, rather than treating an allowlisted snapshot alone as sufficient.

Photo validation must be independent of an honest editor: the server checks raster signatures, bounded dimensions/pixel count and byte size, then rejects or strips JPEG APP/COM and PNG metadata/unknown ancillary chunks before storage. Do not accept SVG, remote image URLs, original private attachment keys or arbitrary metadata-bearing bytes. Test forged MIME types, malformed segments, oversized images and metadata rejection/stripping as well as the browser-generated derivative. The exact preview must show the derivative that will actually be published.

Test-first pure DTO validation/projection and actual handlers with SQLite/D1 fixtures: disabled defaults; exact preview; unknown/nested field leakage; malicious text remains text; owner/member/anonymous writes; cross-owner record/photo/object attacks; private API protection; revoke/update/expiry/cache boundaries; metadata stripping; consent and once-only key response; hash verification, invalid/expired/revoked/rotated/scoped keys; cursor tampering; denied writes; rate counter; equipment snapshot/direct/hire/unknown semantics; no canonical mutations; secret exclusion from backups/support/client artifacts. Two dummy AMZeus/ZeusTek clients only. Four required widths plus320/430, keyboard/focus/console/overflow. Full retained gate and nine frozen hashes.

## Rollout, approval and recovery

Additive schema/artifacts only; no owner record migration. Ship publication disabled and no issued keys unless exact later consent is obtained. Local fixtures prove full capabilities without production synthetic records. Production smoke reads status/disabled visitor page/auth and verifies security/cache boundaries; never publishes profile or creates keys implicitly. Rollback restores the then-current accepted Sites artifact; disable publication/revoke keys if a newly enabled capability fails. Preserve source/evidence. Accepted source goes to GitHub only after live release verification.
